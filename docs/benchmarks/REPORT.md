# Qwen3.8-27B on one RTX 4090: PoC report

- Dates: 2026-09-23 (host 1) and 2026-09-24 (host 2).
- Question: can one rented RTX 4090 serve Qwen3.8-27B to a team using pi, and with which engine and quant?
- Measured numbers come from `results/raw/*.summary.json`, `results/llamabench/` and `results/evidence/`.
- External numbers (file sizes, publisher accuracy, Cloudflare limits) are marked and listed in `results/evidence/external_sources.txt`.
- Full tables with every config: [FINDINGS.md](FINDINGS.md) (generated by `bench/compare.py`).

## Verdict

- **Yes, for a small team.** One 4090 served 8 agents at once with ~5 s waits per turn.
- **Engine: vLLM 0.30.** Most throughput under load, and it queues extra requests instead of failing them.
- **Not Ollama for a team.** It runs Qwen3.8 one request at a time, so everyone else waits in line.
- **SGLang is good for up to about 4 agents on 24 GB.** Lowest agent-turn wait (p50) for 1 to 4 agents; its balanced config runs 4 requests at once, so 8 agents waited 18.7 s per turn.
- **Not llama.cpp for a team.** It handled 4 agents slowly and failed some requests at 8.
- **Pool size matters beyond 8 agents.** Up to 8, waits were the same at every int4 pool size; at 12, bigger pools gave shorter waits.
- **Real pi works.** 34 of 34 real pi agent runs passed.
- **gpt-oss-20b is much faster on this card.** With the same cache pool size, 8 agents waited 0.26 s per turn instead of 4.9 s; vLLM was again the best engine under load.

## Cache pool size and capacity

| Config | KV pool (tokens) | 8 agents: turn wait p50 | 12 agents: turn wait p50 / p90 |
|---|---|---|---|
| vLLM fp8, 0.95 (host 1) | 84,898 | 7.4 s | not run |
| vLLM int4, 0.97 (host 1) | 180,558 ¹ | 5.0 s | 11.7 / 29.9 s |
| vLLM int4, pinned 4.5 GiB (host 2) | 246,094 | 4.9 s | 7.4 / 14.6 s |
| vLLM int4, 0.97 (host 2) | 298,255 | 5.1 s | 6.7 / 11.1 s |

- At 8 agents, the three int4 pools gave the same wait: 4.9 to 5.1 s.
- At 12 agents, bigger pools served more input from cache: 12% at 181k, 54% at 246k, 69% at 298k.
- Waits at 12 agents fell in the same order: 11.7 s, 7.4 s, 6.7 s.
- Likely cause (not isolated): a cache miss means re-reading the whole ~12k-token context.
- ¹ The host-1 server log was later overwritten. The value is kept in the overwrite note in `results/evidence/thinking_ab_and_queueing.txt`.
- For comparison: SGLang's pool was 51,908 tokens (0.5.20; ~52.2k on 0.5.19); llama.cpp used a 65,536-token shared pool.

### Why the pool is pinned instead of using 0.97

- vLLM sizes its pool from a memory profiling run.
- That run measured 2.7 GiB of activations on host 1 and 0.5 GiB on host 2, with the same flags.
- On host 2 the int4 run at 0.97 (298k pool) passed its whole suite.
- On host 2 the fp8 run at 0.97 (164,584-token pool) crashed: a CUDA out-of-memory at 4 concurrent requests. All later requests failed.
- Pinning 4.5 GiB keeps about 1 GB of headroom and does not depend on the profiler.

## Multiple users, multiple agents

Test setup:
- Each user's agents share a ~6k-token repo context after pi's system prompt, then get their own task.
- All agents start within 3 s. 8 turns each.
- Contexts averaged 12.8k to 13.2k tokens (the capacity test above averaged 6.9k).
- Server: the recommended config.

| Mix | Agents | Turn wait p50 / p90 | Tok/s per agent | Input from cache | Session time | Errors |
|---|---|---|---|---|---|---|
| 4 users x 3 agents | 12 | 11.0 / 53.0 s | 11.5 | 52% | 307 to 309 s | 0 |
| 1 user x 8 agents + 4 users x 1 agent | 12 | 10.1 / 35.7 s | 11.4 | 53% | 310 to 313 s | 0 |

- Agents of one user reuse that user's shared context.
- The 2nd and 3rd agents found 6,208 to 7,760 of their 7.1k to 8.2k opening tokens already cached.
- Reuse comes in 1,552-token blocks on this model (see the architecture section).
- Starting 12 agents within 3 s queued their first turns: 7 to 13 s for new contexts.
- One light user's context repeated from the previous run: its first turn took 1.0 s (82% cached).
- The p90 wait reached 53 s. That is inside Cloudflare's 100 s limit, but not by much.
- Longer contexts cost more: 12 agents at a 6.9k average waited 7.4 s (p50) and 14.6 s (p90).

Fairness, with one heavy user and four light users:

| User | Agents | Turn wait p50 / p90 |
|---|---|---|
| Heavy user | 8 | 9.4 / 33.7 s |
| Each light user | 1 | 10.6 to 18.6 / 28.8 to 38.4 s |

- vLLM serves requests first come, first served. It has no per-user fairness.
- One user running many agents slows everyone. The light users were not protected.
- Possible fixes, not tested: per-person keys with a per-key request cap at the gateway, or vLLM's priority scheduling.

## How long context stays cached between turns

- pi keeps the full conversation on the Mac. Nothing is lost when the server forgets.
- vLLM frees cached context least-recently-used first when it needs space (its design).
- 0% in the table means that probe's next turn found nothing cached and re-read its whole context.

Test:
- Each idle gap used its own ~12k-token context. All contexts were built at about the same time.
- After its gap, each context got one more turn. Cell = share of that context still cached.
- So each cell answers: was a context idle this long still cached? It does not track one context over time.

| Idle gap | Quiet server | 4 other agents running | 8 other agents running |
|---|---|---|---|
| 5 s | 93% | 93% | 93% |
| 30 s | not run | 94% | 0% |
| 1 min | 94% | 97% | 0% |
| 2 min | not run | 0% | 0% |
| 4 min | not run | 0% | 0% |
| 5 min | 97% | not run | not run |
| 8 min | not run | invalid (setup request failed) | 0% |
| 15 min | 88% | not run | not run |

- Quiet server: every context was still cached, including the one idle 15 minutes.
- 4 other agents: contexts idle up to 1 minute were cached; those idle 2 or 4 minutes were not.
- 8 other agents: only the context idle 5 seconds was cached; those idle 30 seconds or more were not.
- Cached turns on a quiet server started in 0.3 to 0.8 s (the 5 s probes queued behind the other probes' setup).
- After an eviction, a ~12k-token turn took 5.7 to 21 s to start (the re-read queued behind the other agents).
- Measured cold re-read on this config: ~7.4 s for 16k tokens, ~18.4 s for 32k.
- Only one pool size was tested. A bigger pool should keep contexts longer (expected, not measured).

## gpt-oss-20b on the same card

Why this model: a different architecture on the same GPU.

| | Qwen3.8-27B | gpt-oss-20b |
|---|---|---|
| Architecture | Dense, hybrid (48 Gated DeltaNet + 16 full-attention layers) | MoE, 21B total, 3.6B active (external); 12 sliding-window (128) + 12 full-attention layers |
| KV per token (bf16, from configs) | 64 KiB, plus 75 MiB fixed state per session (fp16) | 24 KiB, plus 3 MiB of sliding-window cache per session |
| Weights on GPU (vLLM) | 16.59 GiB | 13.7 GiB |
| KV pool (vLLM, pinned) | 246,094 tokens | 246,214 tokens |
| Prefill, 16k prompt | 2,199 tok/s (7.4 s) | 13,196 tok/s (1.2 s) |
| Decode, 1 user | 52.5 tok/s | 197.6 tok/s |
| Decode, 16 at once (total) | 357 tok/s | 1,019 tok/s |
| Agent turn wait p50, 8 / 16 agents | 4.9 / 16.5 s | 0.26 / 0.88 s |
| Input from cache, 8 agents | 69% | 79% |

- Both pools are the same size, so cache size does not explain the gap.
- gpt-oss agent replies stopped naturally (64 to 74 tokens) instead of a forced 150. Compare turn waits, not session times.
- Why: forcing a fixed length (`ignore_eos`) made vLLM's gpt-oss parser end the stream with an error.
- Quality was not compared. This is speed only.

| Decode, 1 user (tok/s) | 197.6 | **242.6** | 191.8 | 24.3 |

- \* Same with gpt-oss: the 34.1k prompt was silently cut to 16,386 tokens. Each slot had 32k (4 slots, 131,072 tokens in total).

- llama.cpp has the fastest single stream. vLLM wins as soon as several agents run.

## What depends on the architecture

Cache cost per architecture (`bench/fit.py --shape-only` on the configs in `models/configs/`, bf16 KV, fp16 state):

| Model | Architecture | KV per token | Fixed cost per session |
|---|---|---|---|
| Qwen3-32B | Full attention, dense | 256 KiB | none |
| Qwen3-30B-A3B | Full attention, MoE | 96 KiB | none |
| gpt-oss-20b | Half sliding window (128 tokens) | 24 KiB | 3 MiB |
| Muse Glimmer 30B | 3/4 sliding window (2k tokens) | 13 KiB | 78 MiB |
| LFM2-8B-A1B | Hybrid, short convolutions | 12 KiB | 0.2 MiB |
| Qwen3.8-27B | Hybrid, Gated DeltaNet | 64 KiB | 75 MiB |

- KV per token sets how many tokens fit in a given pool. It is one input to capacity and cache survival; traffic is the other (survival measured for Qwen3.8 only).
- For Qwen3.8, the large per-session state is behind vLLM's 1,552-token cache blocks and SGLang's per-request state slots.
- LFM2 is also a hybrid, but its state is tiny.

Which findings carry over:

| Finding | Qwen3.8 (hybrid, measured) | gpt-oss-20b (sliding + full, measured) | Other full-attention models (not measured) |
|---|---|---|---|
| vLLM is the best engine under load | Yes | Yes | Likely |
| Ollama runs requests in parallel | No (`-np 1`) | Yes (`-np 4`) | Likely yes |
| SGLang is competitive | No: state slots cap it at 4 requests | No: slow here (possibly its MXFP4 kernel) | Not measured |
| Prefix cache reuse granularity (vLLM) | 1,552-token blocks | 16-token blocks (engine default) | 16-token blocks by design (not measured) |
| llama.cpp fails requests when the shared pool overflows | Yes (8 agents) | Not reached at 8 agents (small KV) | Yes, if the pool overflows |
| Pin vLLM's KV memory (after the fp8 crash at 0.97) | Recommended | Pinned here too | Not tested |
| First-come-first-served, no per-user fairness | Yes | Same scheduler | Yes (engine behaviour) |

- A probable contributor: 3.6B active parameters vs 27B. Not isolated: replies and cache hits also differed.
- Engine choice depends on the architecture and the weight format. Test a new model with `run_suite.sh` before choosing.

## Pitfalls hit (and fixes)

| Problem | Fix |
|---|---|
| Default vLLM/SGLang wheels need CUDA 13; host 1 had CUDA 12.8 | vLLM `+cu129` wheel; SGLang 0.5.19 with a cu129 swap. Host 2 (driver 580) needs neither |
| FlashInfer JIT failed (`nvcc` 12.4 too old) | Install `cuda-nvcc-12-8`, set `CUDA_HOME` |
| llama.cpp failed requests at 8 agents | Shared pool overflow. Use per-slot caps, or use vLLM |
| llama.cpp lost prefix reuse on this hybrid model | `-cms 1024` (checkpoint every 1k tokens) |
| Ollama ignored `OLLAMA_NUM_PARALLEL` | Forced to 1 for this architecture. No fix found in 0.34.3 |
| SGLang capped at 2 running, then out of memory | Tuned to 4 running. Unified memory did not help |
| vLLM fp8 at 0.97 crashed at 4 users (host 2) | Profiler underestimated activations. Pin KV memory explicitly |
| MTP would not boot with fp8 KV at 65k | Only fits with int4 KV. Not worth it for agents |
| Root disk filled; all tmux jobs died | Keep caches on `/workspace` |
| vLLM `/invocations` open without key | Gateway in front |
| Gateway gave random 401s with the right key | Restarts left old Caddy processes on the same port (`SO_REUSEPORT`). Start script now kills by process and checks for 1 listener |
