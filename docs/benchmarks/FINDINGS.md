# Qwen3.8-27B on one RTX 4090: findings

Date: 2026-09-23. Box: RunPod pod, RTX 4090 24,564 MiB (driver 570.211, CUDA 12.8), Ryzen 9 7950X, 61 GB RAM,
EU-RO-1. Every number below comes from `results/raw/` (tables between the `compare` markers are generated by
`bench/compare.py`; nothing inside them is typed by hand). Load generator, prompts and seeds are identical across
engines and run on the pod itself, so network is not in the numbers.

## Answer

- **Ollama is not enough for a team.** Ollama 0.34.3 refuses to run Qwen3.8 in parallel
  (`model architecture does not currently support parallel requests architecture=qwen35`, whatever
  `OLLAMA_NUM_PARALLEL` says). Every request queues behind the previous one: total output stays at ~78 tok/s from
  1 to 16 users, and at 16 concurrent the median wait for a first token is 49 s. It also silently cut a 35.2k-token prompt to 16,386 tokens.
  It is a good single-user server: MTP is on by default and gives ~102 tok/s decode.
- **SGLang runs, but not well on 24 GB.** The last CUDA 12 build (0.5.19) boots with CUDA graphs on the 4090, and
  with 1 to 2 users it matches vLLM on decode and has the lowest agent-turn latency measured (0.55 s). Its hybrid-model cache reserves 3 to 5 Gated DeltaNet state
  slots (78 MB each) per running request and it cannot drop the vision tower for this model, so on 24 GB you choose
  between 8 running requests with a 23.5k-token KV pool (smaller than one 32k prompt) and 4 running requests with a
  52k pool. At 4 running, the 8th and 16th concurrent users queue (10 s and 26 s to first token).
- **vLLM 0.30 is the team engine.** Highest throughput under load (357 to 368 tok/s total at 16 concurrent vs 78 to
  141 for the others), working prefix caching on the hybrid model, and the only engine that stayed up and error-free
  through every load level once its KV memory was pinned. int4 KV cache (`int4_per_token_head` on the Triton attention
  path) roughly doubles the pool over fp8 at a 2% single-user decode cost (up to 12% per user at 8 concurrent) and
  a slower cold prefill on long prompts (32k: 1,769 vs 2,145 to 2,568 tok/s, 18 s vs 13 to 15 s).
  **Recommended config: `vllm-int4-kv4-pin` in `pod/serve.sh`** (int4 KV, `--kv-cache-memory-bytes` 4.5 GiB =
  246k-token pool). Do not size the pool with `--gpu-memory-utilization` alone: see finding 16 (fp8 KV at 0.97 crashed
  the server with a runtime out-of-memory on host 2).
- **Cache pool size sets capacity beyond 8 agents.** With pi-shaped sessions of ~12.6k tokens, the recommended config holds
  8 agents working at the same moment at 4.9 s median time to first token per turn (p90 7.2 s, 30 tok/s each);
  12 at once is where it starts to degrade (7.4 s, p90 14.6 s, 21 tok/s), and 16 is past the cliff (16.5 s, 6 tok/s).
  The ceiling scales inversely with context: by the pool arithmetic (not measured), sessions that grow to ~30k
  tokens leave room for about 4 to 5 active agents. A team of 10 to 15 whose agents are not all mid-turn at once
  should fit; 12 or more agents grinding simultaneously will queue.
- **MTP (speculative decoding) is a single-user feature.** On vLLM it lifts one user from 52.5 to 82.3 tok/s, but it
  costs 72k tokens of KV pool and cuts prefix-cache hits (77% to 51% for one agent), so agent sessions are no faster
  with 1 agent and slower from 2 agents up (8 agents: 236 s vs 101 s per session).
  Leave it off for the team server.

## Right-sizing Qwen3.8-27B for 24 GB

Architecture (from `config.json`, `models/configs/qwen3.8-27b.json`): 64 layers, only 16 of them full attention
(4 KV heads x 256), 48 Gated DeltaNet layers with a fixed-size recurrent state. `bench/fit.py` turns that into:

| quantity | value |
|---|---|
| KV cache per token (16 full-attention layers) | 64 KiB bf16, 32 KiB fp8, 34 KiB q8_0, 16 KiB int4 |
| Gated DeltaNet state per sequence (constant) | 146.8 MiB fp32 (llama.cpp), 74.8 MiB fp16 (vLLM `--mamba-ssm-cache-dtype float16`) |
| official FP8 checkpoint | 28.75 GiB: does not fit |

Quant choice:

- **vLLM / SGLang: `RedHatAI/Qwen3.8-27B-INT4`** (compressed-tensors W4A16, group 128, Marlin kernels on sm89,
  18.12 GiB on disk, 16.59 GiB on the GPU with `--language-model-only`). Red Hat publishes 98.5 to 99.7% recovery
  on IFEval / MMLU-Pro / GPQA / AIME25. It keeps the MTP head, so MTP stays an option.
- **llama.cpp: `unsloth/Qwen3.8-27B-GGUF` UD-Q4_K_XL** (16.35 GiB). Engine-only quant ladder (q8_0 KV; last column from `llama-batched-bench`, the rest from `llama-bench`):

  | file | GiB | prefill 4k tok/s | decode tok/s, empty / 32k context | decode, 16 sequences total |
  |---|---|---|---|---|
  | UD-IQ4_XS | 13.27 | 3,061 | 55.7 / 49.7 | 368 |
  | UD-Q4_K_XL | 16.35 | 2,958 | 47.3 / 42.9 | 336 |
  | UD-Q5_K_M | 18.41 | 2,767 | 42.5 / 38.9 | 308 |

  Decode speed follows file size (consistent with a memory-bandwidth bound; inferred, not measured). Q5 is 10%
  slower and leaves ~2 GB less for the KV cache. IQ4_XS is 18% faster and 3 GB smaller; its quality versus
  UD-Q4_K_XL was not measured and no published comparison was found (published KLD vs BF16 exists for UD-Q4_K_XL:
  0.0096). UD-Q4_K_XL is the default, IQ4_XS the capacity option.
- **Ollama: `qwen3.8:27b`** = Q4_K_M 15.66 GiB + 0.87 GiB vision projector, MTP draft 4 by default.

## Host 2 (2026-09-24): same volume, driver 580 / CUDA 13

The pod moved to a second RTX 4090 host (`lvfz66wmg22ns1`, same EU-RO-1 volume, driver 580.159 = CUDA 13.0).
`pod/bootstrap.sh` restores a fresh container in a few minutes; models, the vLLM venv and caches are on the volume.

- **Reproduction:** the int4-KV vLLM config reproduced host 1 within 2% on prefill and per-user decode, within 5%
  on total decode throughput (2 at once: 86.5 vs 82.5 tok/s), and within ~7% on agent cells up to 4 users (rows
  `vllm/int4-kv4` vs `vllm/int4-kv4-h2`).
- **Bigger pool, same flags:** vLLM's profiler measured a much smaller activation peak here (finding 16), so 0.97
  utilisation gave a 298k-token pool instead of 181k. That moved the 12-agent cliff out (12 agents: 6.7 s per turn and
  69% prefix hits vs 11.7 s and 12%), but the same effect crashed the fp8 run, so the recommendation is now the
  pinned 246k pool, which behaves like the 298k one up to 8 agents and degrades at 12.
- **SGLang 0.5.20** (CUDA 13, installs with a plain `uv pip install` on this driver) was within 2% of 0.5.19 on
  prefill and decode with the same flags (4-agent turn wait 1.5 s vs 1.7 s); `--enable-unified-memory` did not lift its 4-request cap (findings 14, 15).
- **fp8 KV on this host** prefilled 17 to 18% slower than on host 1 at 4k to 16k with the same FlashInfer backend;
  int4 KV did not change between hosts. Not explained; the fp8 run then crashed (finding 16), so it was not repeated.
- **pi:** 8 of 8 real pi agents passed against the pinned config with thinking on (34 of 34 runs across both hosts).

## Things that broke, and why (each reproduced here)

| # | What | Cause / fix |
|---|---|---|
| 1 | `pip install vllm` / `sglang` default wheels do not run on this host | Both default to CUDA 13 (torch 2.13 cu130); the pod's driver 570 supports CUDA 12.8. vLLM ships a `+cu129` wheel (installed); SGLang 0.5.20 is CUDA 13 only, 0.5.19 installs via its documented cu129 swap (`pod/install_sglang.sh`, `pod/fix_sglang_cu129.sh`). A host with driver >= 580 removes all of this. |
| 2 | vLLM died in CUDA-graph capture: `nvcc fatal: Unknown option '--compress-mode=size'` | FlashInfer JIT needs nvcc >= 12.8; the image has 12.4. `apt-get install cuda-nvcc-12-8 ...` and `CUDA_HOME=/usr/local/cuda-12.8`. Also `ninja` must be on PATH (venv `bin/`). |
| 3 | llama.cpp failed 8 of 54 requests at 8 agents: 5 rejected with `Context size has been exceeded`, 3 cut off mid-stream (found by a later audit) | With `--kv-unified` all slots share one pool; when the sum of live contexts overflows it, requests fail instead of queueing. vLLM queued instead (0 errors; up to 13 requests waiting in the pinned run). For llama.cpp, give each slot a fixed share (`--no-kv-unified`, e.g. 4 x 32k) and set pi's `contextWindow` to that share. |
| 4 | llama.cpp prefix reuse on the hybrid model | It can only resume at a saved state checkpoint; default spacing is 8,192 tokens. `-cms 1024` gave 78% cached tokens per agent turn. |
| 5 | vLLM MTP at fp8 KV would not boot at 65k context | MTP head + graphs leave 1.91 GiB of KV, less than one 65k request. Needs int4 KV (pool 109k). |
| 6 | vLLM prefix-cache granularity | Attention blocks are stretched to the size of one GDN state page: 800 tokens at fp8 KV, 1,552 at int4. A new turn re-prefills up to one block of the reused prefix. |
| 7 | SGLang capped itself at 2 running requests | Default radix strategy reserves 5 state slots per request. `--mamba-radix-cache-strategy no_buffer` (3 slots, needs `--disable-overlap-schedule`) + `--max-mamba-cache-size`. 8 running requests left a 23.5k KV pool; 4 is the balance. |
| 8 | SGLang ran out of memory on the first 2k-token prefill | Vision tower stays loaded (`--language-model-only` in 0.5.19 only supports MuseGlimmer) and a second process holds 448 MB. `--cuda-graph-backend-prefill disabled`, `--mem-fraction-static 0.88`. |
| 9 | Ollama ignores `OLLAMA_NUM_PARALLEL` for this model | `sched.go: model architecture does not currently support parallel requests architecture=qwen35`; the runner starts with `-np 1`. |
| 10 | Ollama cut a 35.2k-token prompt to 16,386 tokens with no error (same for gpt-oss: 34.1k to 16,386) | Context was 32,768 tokens (set via `OLLAMA_CONTEXT_LENGTH`) with context shift on; prompts under the limit passed intact. |
| 11 | Root disk filled during the SGLang install and took every tmux job with it | 20 GB container disk. JIT caches now live on the volume (`FLASHINFER_WORKSPACE_BASE`, `TRITON_CACHE_DIR`, `VLLM_CACHE_ROOT` in `/workspace/env.sh`). |
| 12 | Network volume quota (~93 GiB) hit mid-download | Models + one vLLM venv + Ollama's copy is ~86 GB. HF downloads run at ~800 MB/s on this host, so deleting and re-fetching a model costs about a minute. |
| 13 | vLLM takes 8 to 13 minutes to become ready | Python imports from the network volume (~3 min), weight load 78 s, first-boot FlashInfer JIT. Later boots reuse the JIT cache (~8 min). |
| 14 | SGLang 0.5.20 (host 2, CUDA 13) is no better than 0.5.19 with the same flags | 51.9k pool (0.5.19: ~52.2k), 4 running requests, prefill and decode within 2%; 4-agent turn wait 1.5 s vs 1.7 s; `--cuda-graph-max-bs` became ambiguous (use `--cuda-graph-max-bs-decode`). `--language-model-only` still only covers MuseGlimmer/Cosmos3. |
| 15 | SGLang `--enable-unified-memory` does not lift the cap | With fp8 KV the Triton attention kernel gets the pool's raw uint8 bytes and fails to compile ("only int8 supported!" in `tl.dot`). With bf16 KV it boots but still derives `max_running_requests=2` from a nominal 10-slot state cache; forcing 48 state slots leaves no room for KV ("Loaded weights leave no GPU memory for the KV cache"). |
| 16 | vLLM's KV pool size depends on cache state, and a large pool can crash the server | The pool is VRAM x `--gpu-memory-utilization` minus a *profiled* activation peak. That peak measured 2.71 to 2.84 GiB on host 1 and 0.50 to 0.54 GiB on host 2 (same flags; host 2 had a warm torch-compile cache on the volume, the likely cause, not proven). With the low estimate, fp8 KV at 0.97 got a 164.6k pool and then died of a runtime CUDA OOM (58 MiB short) on the first 4-request batch: every request failed. int4 KV at 0.97 (298k pool) survived its suite with a thin margin. Fix: pin `--kv-cache-memory-bytes` (4.5 GiB = 246k int4 tokens) instead of trusting the profiler. |

## pi end to end

`bench/pi_team.py` ran real `pi -p` agents (pi 0.84.2) on this Mac against `vllm-int4-kv4` through
`scripts/tunnel.sh`: three small Python repos (fix a stats module, implement `slugify`, fix an LRU cache), each with a
failing unittest suite; pass = the suite passes afterwards and the test files are untouched. Table in the generated
section above. All 26 runs passed with thinking off and with pi's `medium` (verified: the event stream carries
`thinking` blocks). With thinking on, 8 agents at once finished in 70 s (median 49 s per agent vs 24 s for one
agent alone). These tasks are small (4 to 15 tool calls, contexts under 10k tokens); they prove the tool-call path
(vLLM `qwen3_coder` parser + `qwen3` reasoning parser + pi's `qwen-chat-template` thinking format) and concurrency
behaviour, not model quality on real work.

ignores. `input` is text only because the server runs `--language-model-only`.
